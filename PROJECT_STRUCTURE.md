# Структура проекта Townhouse

## Обзор
Проект представляет собой SPA (Single Page Application) для управления жилищно-коммунальным хозяйством. Разработан на React с использованием Refine framework.

**Архитектура учёта показаний и начислений построена по принципу "документ → регистр":**
- **Документы** (`meter_reading_documents`, `accrual_documents`) — это шапки операций: массовый ввод показаний или начисление за период создаёт документ, который группирует связанные записи и хранит общие атрибуты (название, дата, вид услуги).
- **Регистры** (`meter_readings`, `accruals_register`) — это плоские таблицы фактических записей (конкретное показание конкретного счётчика, конкретное начисление конкретному лицевому счёту), каждая запись опционально ссылается на породивший её документ через `document_id` / `accrual_document_id`.
- Удаление документа каскадно удаляет все связанные записи регистра (`ondelete="CASCADE"`).

## Технологический стек
- **React 18** - библиотека для построения пользовательских интерфейсов
- **Refine** - фреймворк для CRUD-приложений
- **React Router v6** - маршрутизация в приложении
- **Ant Design** - библиотека компонентов UI
- **TypeScript** - типизированный JavaScript
- **Vite** - сборщик и dev-сервер
- **Docker** - контейнеризация приложения
- **dayjs** - работа с датами и временем

### 2. `pages/GenericList.tsx` - Универсальная страница (~450 строк)

**Что делает:**
- Отображает таблицу с данными для любого ресурса, включая `meter_reading_documents` и `meter_readings`
- Обрабатывает CRUD операции (Create, Read, Update, Delete)
- Управляет модальными окнами
- Интегрируется с метаданными бэкенда

**Ключевые особенности:**
- Динамически строит таблицу на основе конфигурации

- Регистры (`accounts_register`, `accruals_register`, `meter_readings`) — только чтение и **без столбца «Действия»**: записи формируются документами, прямое редактирование/удаление недоступно

### 7. `components/meter-readings/BulkReadingsModal.tsx`

**Что делает:**
- Массовый ввод показаний счетчиков с автоматическим созданием документа-шапки (`meter_reading_documents`)
- Показывает список всех квартир
- Позволяет вводить показания для каждой квартиры
- Автоматически проверяет ошибки
- На бэкенде автоматически подбирается счётчик по квартире и виду услуги, если он явно не указан

**Бизнес-логика:**
1. Оператор вводит название документа (например, «Показания за август 2026»)
2. Выбирает вид услуги (вода, свет, газ) и дату показания
3. Вводит показания напротив каждой квартиры
4. Пустые строки пропускаются
5. POST `/api/meter_readings/bulk` создаёт один `MeterReadingDocument` и набор связанных с ним `MeterReading`
6. Ошибки по отдельным строкам показываются в таблице, не прерывая сохранение остальных строк

Модалка работает в двух режимах:
- **Создание** (без `documentId`): оператор заполняет форму, создаётся новый документ показаний.
- **Редактирование** (с `documentId`): данные и показания существующего документа подгружаются через `GET /api/meter_reading_documents/{id}/readings`, а при сохранении документ полностью пересоздаётся через `PUT /api/meter_reading_documents/{id}/full` (старые строки удаляются, создаются новые из присланного списка).

---

### 8. `components/accruals/AccrualsCalculationModal.tsx`

**Что делает:**
- Расчет начислений за период
- Предварительный просмотр
- Выборочное сохранение

**Бизнес-логика:**
1. Оператор выбирает месяц/год
2. Система рассчитывает начисления по всем счетам (GET `/api/accruals_register/calculate`)
3. Отображается таблица с предварительными строками
4. Оператор выбирает строки для сохранения
5. Выбранные строки сохраняются в регистр (POST `/api/accruals_register/generate`)

Модалка работает в двух режимах:
- **Создание** (без `documentId`): создаётся новый документ начислений.
- **Редактирование** (с `documentId`): месяц/год и ранее выбранные пары (account_id + services_type_id) подгружаются через `GET /api/accrual_documents/{id}/details`, а при сохранении строки документа полностью пересоздаются через `PUT /api/accrual_documents/{id}/full` (старые строки и связанные записи `accounts_register` удаляются).

**Важно (защита от подмены данных):** клиент отправляет на сервер только идентификаторы выбранных пар `(account_id, services_type_id)`. Сумма, потребление, тариф и показания всегда пересчитываются на сервере на момент сохранения, поэтому изменившиеся между предпросмотром и сохранением данные не искажаются.


```
    ↓
RecordFormModal → поля из метаданных
    ↓
Пользователь заполняет форму
    ↓
useCreate() → POST /api/{resource}
    ↓
Обновление таблицы
```

### 3. Массовый ввод показаний
```
Пользователь открывает модалку из раздела «Документы показаний»
    ↓
BulkReadingsModal → загрузка квартир и видов услуг
    ↓

счётчик для каждой квартиры подбирается автоматически, если не указан явно
    ↓
Обработка ошибок поотдельным строкам и успех
```

Удаление документа показаний (`DELETE /api/meter_reading_documents/{id}`) каскадно удаляет все связанные с ним записи в `meter_readings` на уровне БД (`ondelete="CASCADE"`).

```
Пользователь выбирает период
    ↓
GET /api/accruals_register/calculate
    ↓
Отображение предварительных строк
    ↓
Пользователь выбирает строки
    ↓
POST /api/accruals_register/generate
    ↓
Сохранение в регистр
```

## 🗄️ Бэкенд (`backend/`)

### Стек: FastAPI + SQLAlchemy + PostgreSQL

### `models.py` — модели СУБД
Ключевые модели, реализующие разделение документ/регистр:

| Модель | Таблица | Роль |
|-------|--------|------|
| `MeterReadingDocument` | `meter_reading_documents` | Документ-шапка: название, дата, вид услуги |
| `MeterReading` | `meter_readings` | Строка регистра: конкретное показание, ссылается на `document_id` |
| `AccrualDocument` | `accrual_documents` | Документ-шапка начислений: дата, `title` (название) |
| `AccrualsRegister` | `accruals_register` | Строка регистра начислений, ссылается на `accrual_document_id` |

`MeterReading` также хранит `apartment_id` напрямую (не только через `meter_id`), что позволяет вносить показания даже без привязанного счётчика.

Удаление документа каскадно удаляет связанные строки регистра (`ForeignKey(..., ondelete="CASCADE")`).

### `app.py` — API
- Универсальные CRUD-эндпоинты `GET/POST/PATCH/DELETE /api/{resource}` через `MODEL_MAP` / `SERIALIZERS` / `FIELD_CONFIG`
- `GET /api/meta/{resource}` — метаданные полей для динамической формы на фронте
- Кастомные билдеры значений (`CUSTOM_VALUE_BUILDERS`): для `transactions`/`payments` и `meter_readings` сервер сам подбирает лицевой счёт/счётчик по квартире и виду услуги
- Документы «Приход/Расход» (`transactions`/`payments`) имеют поле `title` — название формируется автоматически по формуле «Тип операции + №(ID) + дата операции» (например, «Приход в кассу №17 от 24.08.2026») в момент создания и пересчитывается при изменении типа/даты операции
- `POST /api/meter_readings/bulk` — создаёт `MeterReadingDocument` и набор `MeterReading` за один запрос, автоподбор счётчика по квартире/виду услуги
- `GET /api/meter_reading_documents/{id}/readings` — детализация показаний конкретного документа
- `PUT /api/meter_reading_documents/{id}/full` — полное пересоздание документа показаний (редактирование)
- `GET/POST/PATCH/DELETE /api/accrual_documents` — жизненный цикл документов начислений
- `GET /api/accrual_documents/{id}/details` и `PUT /api/accrual_documents/{id}/full` — детализация и полное пересоздание строк документа начислений
- `GET /api/accruals_register/calculate` и `POST /api/accruals_register/generate` — расчёт и сохранение начислений в регистр

Документы начислений имеют поле `title` (название): оно сериализуется, принимается при создании/обновлении/генерации, а при отсутствии авто-генерируется из `accrual_date` (например, «Начисление за август 2026»).

Регистр `accounts_register` закрыт для прямого создания/изменения/удаления (403) — записи формируются исключительно документами (платежи через SQLAlchemy `event` на `Transaction`, начисления через документы начислений). Строки начислений дополнительно хранят `services_type_id` (вид услуги), который заполняется при записи документа начисления в регистр и отображается в списке/формах. Балансы (`balance_after`) пересчитываются «с нуля» по истории операций аккаунта: при любой вставке/изменении/удалении платежа или пересоздании/удалении начислений выполняется кумулятивный пересчёт всех записей аккаунта в хронологическом порядке (`operation_date`, затем `id`), а не «последняя запись + дельта». Это гарантирует согласованность сальдо даже после правок/удалений операций.

Регистры показывают название документа-источника (`document_title`): в `accruals_register` — название документа начислений (`accrual_document.title`); в `accounts_register` — название начисления либо название документа «Приход/Расход» (`transaction.title`), в зависимости от того, что создало запись.

Протокол списков совместим с `@refinedev/simple-rest`: параметры `_start/_end/_sort/_order`, ответ — JSON-массив с заголовком `X-Total-Count`.

### Запуск через nginx
```
Браузер → nginx (townhouse.sagacloud.kz)
    → location /        → 127.0.0.1:5173 (Vite dev-server)
    → location /api/    → 127.0.0.1:8000 (FastAPI, без отрезания префикса!)
```
Важно: `proxy_pass` для `/api/` должен быть без завершающего слэша (`http://127.0.0.1:8000`, а не `http://127.0.0.1:8000/`), иначе nginx срезает префикс `/api/`, а бэкенд (`APIRouter(prefix="/api")`) его ожидает.

```bash
# Перезапуск фронтенда

# Просмотр логов

docker compose up -d --build frontend
```

### Локальная разработка:
```bash

cd /opt/townhouse/frontend

# Установка зависимостей
npm install

# Запуск dev-сервера (Vite)
npm run dev

# Сборка для продакшена (tsc + vite build)
npm run build

# Проверка TypeScript ошибок
npx tsc --noEmit -p tsconfig.app.json
```
