# Roadmap — Townhouse ERP

Сводный план развития проекта. Дата составления: август 2026.
Все изменения фиксируются в git (ветка `main`), каждое направление — отдельными коммитами.

## 1. Технический долг (из первоначального анализа)

| # | Задача | Обоснование / как |
|---|--------|-------------------|
| 1.1 | Разбить `backend/app.py` (~3000 строк) на модули | ✅ Готово. `app.py` уменьшён с 3035 до ~680 строк. Вынесено: `field_config.py` (`MODEL_MAP`/`FIELD_CONFIG`/`coerce_field_value`), `serializers.py` (сериализаторы/`SERIALIZERS`), `services.py` (8 сервисных функций начислений/транзакций/регистров), `routers/{documents,registers,receipts,others}.py` (спец-эндпоинты). В `app.py` остались auth-роутер, `meta` и generic CRUD. pytest: 30/30 зелёные (см. 3.1). Полный smoke по всем группам — OK. |
| 1.2 | Убрать или оживить `schemas.py` | ✅ Pydantic-модели были неиспользуемы (API на голых `dict`) и устарели (нет новых сущностей/полей). Удалён как мёртвый код. Если при распиле `app.py` (п. 1.1) захочется перейти на типизированные ответы — вести их заново осознанно. |
| 1.3 | Аутентификация и закрыть CORS | ✅ Реализовано: модель `User` + роли, JWT-логин (`/api/auth/login`, `/api/auth/me`, `/api/auth/users`), PBKDF2-хеши, CORS через `CORS_ORIGINS` вместо `['*']`. См. секцию «Аутентификация и ролевой доступ». |
| 1.4 | Ввести миграции БД (Alembic) | ✅ Схема полностью под управлением Alembic. БД на head (`0002_schema_squash`); исторические ручные SQL-миграции (`cash_register`, `services_type.priority`) инкорпорированы в `0002_schema_squash`. Аудит `alembic revision --autogenerate` не выявляет ручных правок сверх моделей; единственный «дрейф» — тип `users.role` (VARCHAR↔Enum, косметический, native_enum=False), зафиксирован в версиях. |
| 1.5 | Серверная сортировка по вложенным полям | ⏳ Частично: реализовано через подзапросы для «№ квартиры» (`apartment.apartment_number`) в регистрах/показаниях и «Документа» (`document_title`) в `accruals_register`. Для произвольных вложенных колонок (напр. `owner.full_name`) общего решения нет — остаётся fallback на `hasattr(model, _sort)`. |
| 1.6 | Почистить «осиротевшие» строки в БД | ⏳ Не подтверждено: не проверялось наличие строк `accounts_register` без привязки к `transaction_id`/`accrual_id` после рефакторинга знаков (миграция `flip_accounts_register_signs.py`). Требуется аудит и проверка целостности (`check_register_integrity`). |
| 1.7 | Проверить пересчёт балансов при массовых правках | ✅ Реализовано: `recalculate_account_balance`/`recalculate_register_balance` «с нуля» + `rebuild_accounts_register` (полная пересборка) + `check_register_integrity`. pytest: `test_payment_update_recalculates_cash_balance`, `test_rebuild_accounts_register_restores_consistency`, `test_rebuild_is_deterministic`. |
| 1.8 | Ни один документ не хранит автора/историю изменений | Выявлено при анализе: `Transaction`, `AccrualDocument`, `MeterReadingDocument`, `ReceiptDocument` не фиксируют `created_by`/`updated_by`/`updated_at`/`change_description`. Функциональная реализация — см. п. 2.9; здесь это учтено как технический долг (нужна целостная аудит-модель для всех документов). |

## 2. UX и функциональность

| # | Задача | Обоснование / как |
|---|--------|-------------------|
| 2.1 | Ресайз и перестановка колонок через библиотеку | Ручная реализация (HTML5 DnD) в AntD Table не заработала при `scroll={{x:'max-content'}}` и была удалена. Надёжно делается через `react-resizable` (ресайз) и `@dnd-kit` / `react-dnd` (перестановка). Требует добавления npm-зависимости. |
| 2.2 | Экспорт регистров и документов в Excel/CSV | Кнопки «Экспорт» в списках; выгрузка с учётом текущих фильтров/пагинации. |
| 2.3 | Отчёты по лицевым счетам | ⏳ Частично: реализован отчёт по одному счёту `GET /api/accounts/{id}/statement` (начислено / оплачено / долг по услугам, внесено / переплата — для отчёта и будущего ЛК). Осталось: сводка по дому / за период, настройка периода в UI. |
| 2.4 | Квитанции: создание, PDF, сохранение | ✅ Реализовано: модели `receipt_documents`/`receipt_items`, генерация по всем счетам за период, долг/переплата на «Фонд развития», PDF через `reportlab` (столбец «Переплата»), реализуем в UI (меню + ReceiptsModal). Осталось: выгрузка ZIP всех квитанций периода, при необходимости брендинг. |
| 2.5 | **Списание — отдельным документом** | Сейчас списание запускается сервисной операцией (`POST /api/write_offs/run`, кнопка/cron/автозапуск при «Приход/Расход») и пишет напрямую в регистры. Перевести на **документ «Списание задолженности»** с собственной моделью (`writeoff_documents`/`writeoff_items`), чтобы у операции были атрибуты документа (дата, №, автор, статус), возможность отмены/пересоздания и записи в журнале. Ядро `calculate_write_offs` при этом остаётся основой, но оборачивается в документооборот. |
| 2.6 | **Настраиваемый доступ к формам/меню (админ)** | Сейчас права ролей зашиты в коде (`permissions.py`, `can.ts`, `menuAccess.ts`). Сделать **форму настроек прав** для администратора, где можно включать/выключать доступ к разделам меню, формам и действиям (создание/изменение/удаление/чтение) по каждой роли. Хранение — таблица настроек доступа (например `role_permissions`), доступ к которой читается в рантайме вместо/в дополнение к зашитым правилам. |
| 2.7 | **Счетчик — только по тарифам «По счетчику»** | При создании счётчика (`meters`) разрешать выбор услуги только тех `services_type`, у которых тип тарифа «По счетчику» (иначе счётчик бессмыслен). Ограничение и на бэкенде (валидация при создании/изменении счётчика), и на фронте (фильтр выпадающего списка внешних ключей). |
| 2.8 | **Переделать обработчики «Выполнить списание»** | Переработать `WriteOffsModal` и обработчики запуска списания (кнопка + автозапуск при «Приход/Расход» + cron), чтобы они опирались на новый документный слой (см. п. 2.5), давали понятный результат/ошибки по каждому счёту и не создавали частичных записей при сбое. |
| 2.9 | **Аудит документов: автор и история изменений** | У каждого документа завести метаданные изменений: `created_by` (автор), `updated_by` (автор последнего изменения), `updated_at` (дата последнего изменения) и при желании `change_description` (что именно изменилось). Сейчас ни один документ не фиксирует автора (`Transaction`, `AccrualDocument`, `MeterReadingDocument`, `ReceiptDocument`). Реализация: миграции на модели + простановка текущего юзера при создании/правке (в generic `create_resource_item`/`update_resource_item` и спец-эндпоинтах) + вывод «Автор»/«Изменён»/«Что изменено» в формах и журнале. Согласуется с п. 2.5 (новый документ списания должен иметь автора с самого начала). |
