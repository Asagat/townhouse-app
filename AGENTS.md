> **Язык:** всегда работай и отвечай только на русском (переход на английский не допускается).

## Первый шаг в каждом новом треде (обязательно читать документацию проекта)
- В **новом** треде/сессии, прежде чем отвечать на запрос или править код, сначала прочитай проектный контекст.
  Даже если задача кажется очевидной — правила и состояние описываются в документации, а не гуглится из кода.
- Обязательный порядок чтения при старте треда:
  1. `AGENTS.md` (этот файл) — контракт правил. Тред должен учитывать их с самого начала;
  2. `.ai/PROJECT_CONTEXT.md` и `.ai/ARCHITECTURE.md` — зачем проект, компоненты и границы слоёв;
  3. `.ai/DEVELOPMENT.md` — как запускать/тестировать/мигрировать.
- Дальше — по теме треда (не всё подряд):
  - если задача касается открытых/выполненных работ и их статусов — `ROADMAP.md`;
  - если касается инфраструктуры запуска/деплоя/БД — `DEPLOY.md`;
  - при работе с конкретным модулем/слоем — релевантные `.ai/*.md` (доменная карта, бизнес-правила, ADR)
    и обзор папок (модель/миграции/страница) до правок кода;
  - запрещённые/устаревшие подходы и принятые решения — см. `.ai/DECISIONS.md` и запреты внизу этого файла.
- Источник истины фактов — код и состояние (живой) БД; доки сверяй с ними и при расхождении
  отмечай `UNKNOWN` и спрашивай, а не выдумывай.

## Architecture & Constraints
- FastAPI backend + React/Refine frontend stack deployed across Proxmox LXC containers.
- Strictly adhere to existing modular patterns; do not introduce conflicting architectural layers.

## Source of Truth
- Backend calculations, validation, and database states are the absolute source of truth.
- Frontend components provide UI presentation and preliminary previews only.

## Database & API Rules
- Use SQLAlchemy and Alembic for database changes and migrations.
- API endpoints must include input validation, proper status codes, and authorization checks.

## Документы и регистры (правила изменения и «перепроводки»)
- **Любое ручное/доверенное изменение данных, документов и регистров — через явный скрипт-миграцию**
  в `backend/migrations/` (dry-run + `--apply`, как прочие), а не «ручной» UPDATE в БД.
- Комментарий к документу начислений хранится в шапке (`AccrualDocument.comment`), у строк регистров
  своего поля нет — строки наследуют основание (комментарий/документ) через связь.
- **При изменении документа (начисления/показания/квитанции/приход‑расход), влияющем на регистры,
  обязательно:**
  1) внести/пополнить пользовательский комментарий (`*.comment` для шапки, у операций — атомная причина);
  2) зафиксировать аудит: `change_description` (+ `updated_by`/`updated_at`);
  3) **«перепровести» регистры** — запустить штатный каскад пересчёта затронутых счетов
     (`recalculate_register_balance`, при необходимости `rebuild_accounts_register`), чтобы срезы
     (`accruals_register`/`accounts_register`) остались согласованы; после — контроль `check_register_integrity`
     и/или сверка контрольных сумм.
- Не менять сумму начисления/строк ``accounts_register`` и не «склеивать» данные вручную в обход пересчёта;
  если требуется правка сумм/тарифов — идти через пересчёт/перепроводку, с комментарием о причине.
- **Разовые правки данных (миграции, реимпорт, ручные скрипты) — после них ОБЯЗАТЕЛЬНО пересчитать
  затронутые счета/регистры штатным механизмом.** Автоматика «документ → регистр» (income из начислений,
  expense-распределение по услугам, ORM-события `transaction_after_*`) срабатывает ТОЛЬКО при изменениях
  через приложение/API. Прямой SQL/скрипт в обход приложения запись в регистре НЕ пересчитывает — срез
  `accounts_register` остаётся от старого состава долгов и «расходится» с документами (реальный случай:
  кв.13 — «Вывоз мусора» 114 500 начислен, но `expense`=0, деньги остались на «Фонде»). Поэтому после
  любой разовой правки данных запусти пересчёт затронутых счетов (`recalculate_register_balance` для
  балансов и, если менялся состав долгов/приходов, `rebuild_accounts_register` или `auto_recalculate_writeoffs`
  для перераспределения expense по услугам) и проверь контроль: `check_register_integrity` и/или сверку
  контрольных сумм. Готовый инструмент для полной сверки «регистр ↔ первичка» и пересчёта рассинхрона —
  `backend/migrations/resync_accounts_register_to_accruals.py` (dry-run + `--apply`); тест-модель —
  `backend/tests/check_sum/test_registers_services_vs_writeoff_model.py`.

## Описательная документация (команда «Обнови описания»)
- Когда пользователь даёт команду **«Обнови описания»** (или «Update the docs»/«обнови ROADMAP»),
  в течение той же сессии обязательно актуализируй **все три файла** и сведи их между собой:
  1. `ROADMAP.md` — статусы задач (перенос выполненного в «Статус уже сделанного», удаление из плана),
     приоритеты и пометки «актуально на <дата>»;
  2. `DEPLOY.md` — модель развёртывания/синопсис окружения и изменения рабочих процессов;
  3. `PROJECT_STRUCTURE.md` — дерево `.github/`/описания файлов и **журнал «Список изменений»**
     (новая строка по каждой выполненной фиче/правке с датой).
- Если правка влияет только на один-два из них — всё равно проверь, не требует ли согласованности остальное,
  и при необходимости дополни их (кратко, без дублирования).
- Источником актуальных фактов являются реализованный код и состояние (живой) БД: не выдумывай детали,
  а сверяй описание с ними (при сомнении отметь `UNKNOWN` и спроси).
