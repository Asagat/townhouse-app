> валидация + отчёт/регистр. Оценка — средняя (≈1–1.5 дня), риск низкий-средний.

## Цель (из формулировки задачи)

Справочник «Кассы/Счета» (`cash_points`) получает **поле «Тип»**: **«Касса»** (наличные)
или **«Счёт»** (банковский). Назначение:
1. **раздельные остатки** — по кассам / по счетам / общий итог;
2. **группировка и фильтр** «Регистра денежных средств» по типу + отдельные
   представления «Наличные»/«Безналичные» (без новых таблиц — фильтр по типу);
3. **валидация** «тип операции документа ↔ тип кэшпоинта» (приход/расход в кассу ↔
   «Касса»; поступление/списание по счёту ↔ «Счёт»);
4. (в перспективе — карточка счёта с банковскими реквизитами; **не** делаем).

Связано с **ТД-6**: остаток уже ведётся по `cash_point_id`, поэтому раздельные
итоги нал/безнал получаются группировкой по типу.

## Факты (текущее состояние)

- `cash_points`: `id, name, is_active` (в БД один кэшпоинт «Касса»; банковских операций нет).
- Тип операции (`TransactionTypeEnum`): `in_cash`(«Приход в кассу») / `out_cash`(«Расход из кассы») /
  `in_bank`(«Приход в банк») / `out_bank`(«Расход из банка»).
- Валидация документа — `services.resolve_transaction_values` (сверяет статью с типом
  операции); кэшпоинт сейчас обязателен, но **его существование/тип не проверяются**.
- Отчёт по кассе (`routers/reports.build_cash_register_report`) уже даёт остатки **по каждой
  кассе** (`opening/income/expense/closing`), JOIN по `t.cash_point_id`.
- Enum-поля уже поддержаны: `field_config` (тип `enum`, `enum_class`) → фронт получает
  `choices`; аналог — `analytic_articles.kind` («Тип» = Доход/Расход).

## Решение (предложение)

**Модель/миграция.** Новый enum `CashPointKind` (`cash = "Касса"`, `bank = "Счёт"`) и
колонка `cash_points.kind` (`Enum(native_enum=False)`, default `cash`, NOT NULL).
Миграция `0023_cash_point_kind`: колонка + бэкфилл существующих («Касса» → `cash`).

**Валидация (backend, источник истины).** В `resolve_transaction_values`:
- кэшпоинт должен существовать (сейчас не проверяется) → 422, если нет;
- `in_cash/out_cash` требуют тип «Касса»; `in_bank/out_bank` — тип «Счёт»; иначе 422 с
  понятным сообщением. Существующие документы (все `in_cash/out_cash` и один «Касса»)
  остаются валидными.

**Сериализаторы.** `cash_point_serializer`: `kind` (метка «Касса»/«Счёт») + `kind_code`
(`cash`/`bank` для логики). В `transaction_serializer`/`cash_register_serializer` —
`cash_point.kind`/`kind_code` рядом с именем.

**Отчёт по кассе.** В `cash_points` добавить `kind`; добавить **итоги по типам**
(«Наличные», «Безналичные», «Общий») — это и есть «раздельные остатки».

**Регистр/фильтр.** Колонка «Тип» + фильтр по типу:
- `sorting.SORT_FIELDS`: `("cash_register","cash_point.kind")` и `("transactions","cash_point.kind")`
  (+ соответственно `cash_points.kind` как прямой столбец);
- `columns.ts`: колонка «Тип» в `cash_points`, `cash_register`, `payments`.

**Форма «Кассы/Счета».** `field_config.cash_points`: поле `kind` (enum) → форма получает
select «Тип»; `formFieldConfig.cash_points = ['name','kind','is_active']`.

## Открытые вопросы
