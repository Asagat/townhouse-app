## Проблема и обоснование
Сейчас денежная операция — один документ `transactions` (с enum-полем
`transaction_type`, значения in_cash/out_cash/in_bank/out_bank) с единым журналом и
общим регистром `cash_register`. Это «документ-хамелеон»:
- реквизиты кассовых и банковских операций разные (в безнале есть БИК/КБЕ/КНП — их нет у кассы);
- нет юридически значимой серии и жизненного цикла (проведён/сторно);
- отмена = физический delete, что недопустимо для аудита УК.

В модели проекта уже есть правильный паттерн «документ → регистр» (accrual_documents,
meter_reading_documents, writeoff_documents): шапка с реквизитами — в таблице документа,
производное движение — в регистре. Денежные документы этому паттерну пока не следуют.

## Целевая архитектура (Вариант А — фиксированный)
Разделяем денежные документы на **два типизированных агрегата-шапки**:

1. **КассовыеДокументы** (`cash_documents`) — наличные:
   - вид: «Приход в кассу» / «Расход из кассы»;
   - хранилище-счёт — «Касса» (cash_point type = касса);
   - реквизиты кассовые (нет БИК/КБЕ/КНП).
2. **БанковскиеДокументы** (`bank_documents`) — безнал:
   - вид: «Поступление на счёт» / «Списание со счёта» (для счетов);
   - хранилище — «Счёт» (cash_point type = счёт/банк);
   - реквизиты банка: БИК/КБЕ/КНП/банковский счёт, держим на карточке банковского счёта
     (кэшпоинт-«Счёт»), а в документ подтягиваются при формировании (документ остаётся лёгким).

Каждый из документов:
- **своя серия нумерации** по (вид + кэшпоинт), номер юридически значимый,
  присваивается при проведении и **не пересчитывается** после записи;
- **свой статус жизненного цикла**: проведён / непроведён / сторнирован;
- **сторно-документом** (обратным), а не физическим удалением — только append/сторно,
  для аудита;
- изменения после проведения — новым (обратным) документом, не правкой.

**Регистры денежных средств** — единый `cash_register` остаётся основным производным
регистром: `cash_point` + `operation_date` + сумма + ссылка на документ-источник.
Журналы «Наличные» / «Безналичные» — это **представления** одного регистра, фильтрованные
по типу (`cash_point.type`); остатки по кассам и по счетам считаются из него.
(Требование владельца «Регистр наличных средств / Регистр безналичных средств» —
удовлетворяем разными страницами регистра, базу не множим.)

## Статусы документа и аудит (обязательно)
- Новая модель жизненного цикла документа:
  - `draft/непроведён` → `posted/проведён` → `reversed/сторнирован`.
- Сторно создаёт зеркальный документ-сторно (`reversed_document_id`), исходный помечается
  сторнированным; строки регистра сторно-документа аннулируют/перекрывают запись исходника.
- Физический delete документов (и их строк регистра) **запрещён** после проведения;
  допустимо удалять только непроведённые (draft) или отдельной админ-операцией с контролем
  целостности.
- Учёт и отчёты читают только проведённые документы (+ учитывают сторно).
