# 2026 — Задача 2.6: настраиваемый доступ к формам и меню (`role_permissions`)

> Задача **2.6** (роадмап, раздел «UX и функциональность»). Тип: новая
> подсистема прав + админ-форма. Оценка — средняя (≈2–3 дня), риск средний
> (затрагивает безопасность: backend остаётся источником истины).

## Статус
- **Дата плана:** 27.09.2026
- **Статус:** реализовано локально (backend + миграция `0022` + фронт + тесты).
  Осталось: релиз `v1.1.N` → выкат → «Обнови описания».
- **Решения:** В1 — материализованная матрица + fallback; **В2 (пересмотрено)** —
  отдельная колонка «Раздел (меню)»; В3 — **вариант B** (CRUD + всё меню); В4 — admin/resident
  фиксированы, `tariff_types` «заперт»; В5 — вкладка внутри «Пользователей».

## Проблема

Права ролей сейчас **зашиты в коде и продублированы в трёх местах**:

| Слой | Файл | Что задаёт |
|---|---|---|
| Backend (истина) | `backend/permissions.py` | доступ к generic CRUD по (метод, ресурс): `_read_allowed` / `_create_update_allowed` / `_delete_allowed`; + `require_write_access` для спец-эндпоинтов |
| Frontend (кнопки) | `frontend/src/auth/can.ts` | `canCreate/canEdit/canDelete(role, resource)` — зеркало backend |
| Frontend (меню) | `frontend/src/auth/menuAccess.ts` | `resourceRoles` — видимость разделов меню |

Роли (`UserRole`): `admin / operator / cashier / controller / auditor / resident`.
Изменить права без правки кода и релиза нельзя. Ручная синхронизация трёх списков
уже даёт риск расхождения (backend и frontend могут разойтись).

## Цель

Админ-редактируемая матрица «роль × ресурс × действие» + видимость пунктов меню.
**Backend — источник истины** (AGENTS.md: «Frontend visibility does not replace
backend security checks»): эндпоинты проверяют права из БД на каждом запросе;
фронтенд лишь отражает их (кнопки/меню).

## Решения (предложение)

**В1. Хранение — материализованная матрица с fallback к дефолтам.**
Таблица `role_permissions` содержит строку на каждую пару (роль, ресурс),
засеянную **текущими** правилами (переносится из `permissions.py` в единую функцию
`default_permissions()`). В рантайме: если строка есть — берём её; если нет (новый
ресурс) — берём дефолт. Это делает таблицу источником истины, но исключает
«случайную блокировку» нового ресурса. Плюс действие «сбросить к умолчаниям».

**В2. Что настраивается (пересмотрено — «Раздел» отдельно от «Чтения»).**
Четыре действия (чтение/создание/изменение/удаление) + **отдельная колонка «Раздел»**
(видимость пункта меню). «Чтение» нельзя совмещать с меню: справочники читаются
формами/фильтрами даже там, где пункт меню не нужен (пример: кассир грузит «Статьи»
для документа «Приход/Расход», хотя в меню их нет). Дефолт «Раздела» — из текущего
`resourceRoles`, «Чтения» — из исторических правил: поведение не меняется.

**В3. Область — выбран вариант B (CRUD + всё меню).**

| Вариант | Охват | Плюсы | Минусы | Оценка |
|---|---|---|---|---|
| A. Минимум | Только generic CRUD; в матрице — **ресурсные** пункты меню | Быстро, малый риск | Отчёты/«Главная»/ЛК-админ остаются ролевыми | ≈1.5 дн |
| **B (выбран)** | A + read-ключи меню (отчёты, `dashboard`, `cabinet_admin`): их эндпоинты проверяют `can_read` | Настраивается **всё меню**; «операции» не трогаем | ~10 эндпоинтов отчётов/дашборда на матричную проверку | ≈2–2.5 дн |
| C. B + «операции» | B + права на начисления/списание/квитанции/показания/пересбор | Полный контроль действий | Больший объём | ≈3–4 дн |

Пользователи (`/api/auth/users`) остаются **admin-only**. `cabinet_admin` — только
видимость раздела: его эндпоинты общие (`/api/accounts/{id}/…`, доступ по `_ensure_can_view_account`).

**В4. Админ и «запертые» ресурсы (подтверждено).**
- `admin` — всегда полный доступ, строка не редактируется (защита от самоблокировки).
- `resident` — фиксировано (только личный кабинет).
- `tariff_types` — системный справочник: создание/изменение/удаление всё равно
  запрещены на уровне бизнес-правила (текущий `LOCKED_RESOURCES`), независимо от прав.

**В5. UI (подтверждено).** Вкладка **«Права доступа»** внутри страницы
«Пользователи и права» (`frontend/src/pages/Users.tsx`) — отдельного пункта меню
не заводим. Форма — матрица: строки — ресурсы (сгруппированы как в меню),
столбцы — роли; в ячейке переключатели **Р** (раздел)/Ч/С/И/У. Кнопки
«Сохранить» и «Сбросить к умолчаниям».

## Изменения в коде

### Backend
1. **`backend/models.py`** — модель `RolePermission`:
   `id, role, resource (String), menu (Boolean), can_read, can_create, can_edit, can_delete,
   updated_at, updated_by (FK users)`, unique `(role, resource)`.
2. **Alembic `0022_role_permissions`** — создание таблицы + идемпотентный сид из
   `default_permissions()`.
3. **`backend/permissions.py`** — рефакторинг:
   - `default_permissions()` — перенос текущих правил (код) в виде данных;
   - каталог ресурсов `PERMISSION_CATALOG` (ключ, подпись, категория — зеркало
     `menu.ts`; выверяется код-ревью/тестом на соответствие);
   - `effective_permissions(db, role)` — DB-строки внахлёст на дефолты;
   - `require_resource_access` читает **из БД** (кэш на время запроса), а не из
     констант; `admin` — безусловно полный. Для варианта B — зависимость
     `require_permission(key)` на read-эндпоинтах отчётов/дашборда; для варианта C —
     матричные проверки на спец-операциях.
4. **`backend/routers/auth.py` (или `others.py`)** — эндпоинты:
   - `GET  /api/auth/permissions/me` — эффективные права текущей роли (для фронта);
   - `GET  /api/auth/permissions`    — каталог + матрица (только admin);
   - `PUT  /api/auth/permissions`    — массовое сохранение (только admin),
     аудит `updated_by/updated_at`;
   - `POST /api/auth/permissions/reset` — сброс к умолчаниям (только admin).

### Frontend
5. **`src/auth/permissions.ts`** (новый) — загрузка/кэш прав текущей роли
   (`GET /permissions/me`), событие `townhouse:auth-change`; ошибка/отсутствие —
   откат к текущим зашитым правилам (плавный переход, без «мигания»).
6. **`can.ts` / `menuAccess.ts`** — читают права из нового стора вместо констант;
   сигнатуры `canCreate/canEdit/canDelete(role, resource)` и
   `hasResourceAccess(role, key)` сохраняем.
7. **`src/components/permissions/RolePermissions.tsx`** (новый) — вкладка «Права доступа» на
   странице «Пользователи» (`Users.tsx`); отдельного пункта меню нет (страница
   и так admin-only).

### Тесты
8. Backend: существующие `tests/test_auth_http.py` (ролевые сценарии) должны
   проходить без изменений (дефолты = текущее поведение). Новые:
   `tests/test_role_permissions.py` — оверрайд меняет доступ (например, снять
   `can_read` у cashier на `owners` → 403), admin не блокируется, reset
   возвращает дефолт, аудит заполняется.
9. Frontend: юнит-тесты `can`/`menuAccess` на данных из стора + тест страницы
   прав (рендер матрицы, сохранение).

## Контроль и риски

- **Блокировка администратора** — запрещена (admin всегда полный, в UI строки
  admin/resident read-only).
- **Расхождение backend ↔ frontend** — фронт больше не хардкодит правила; источник
  один (`/permissions/me`). На время загрузки — дефолты.
- **Кэш прав** — backend читает права на запрос (при желании — короткий
  in-process кэш с инвалидацией после `PUT`); изменения применяются со следующего
  запроса, фронт перечитывает при входе/обновлении.
- **Производительность** — матрица крошечная (≈6 ролей × ~20 ресурсов), лишней
  нагрузки нет.
- **Спец-эндпоинты вне области** (В3) — задокументировать в UI/доках, чтобы не
  создавать ложного ожидания, что ими тоже управляет матрица.
