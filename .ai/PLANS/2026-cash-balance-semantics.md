# 2026 — ТД-6: семантика `cash_register.balance_after` (остаток по кассе)

> Задача **ТД-6** (роадмап, «Технический долг»). Тип: правка бизнес-логики регистра +
> разовый бэкфилл. Оценка — небольшая (≈0.5–1 день), риск низкий-средний.

## Статус
- **Дата плана:** 27.09.2026
- **Статус:** реализовано локально (код + миграция `0021` + тесты + бэкфилл).
  Осталось: релиз `v1.1.8`, выкат на NAS, `--apply` бэкфилла на проде, «Обнови описания».
- **Решения владельца (В1–В3):** В1 = «Остаток по кассе»; В2 = шаг 2 (итог по
  кэшпоинту + `cash_point_id`) делаем сразу; В3 = строку «остаток на начало периода»
  в регистр не добавлять (достаточно отчёта по кассе).

## Проблема (факты, прод 27.09.2026)

`models._REGISTER_RUNNING_UPDATE` считает `balance_after = Σ(income − expense)` **в группе
одного `account_id`** (строки без л/с — отдельная группа `account_id IS NULL`). Для
денежного регистра это сальдо лицевого счёта, а не остаток кассы:

| Показатель | Значение |
|---|---:|
| строк в `cash_register` | 2 130 |
| групп по л/с + группа «без л/с» | 17 + 791 строка |
| **фактический остаток денег (Σ по всей таблице)** | **633 170 ₸** |
| группа «без л/с»: Σ / `balance_after` последней строки | **−58 691 998 ₸** |
| пример, л/с 1: Σ / «Баланс» последней строки | 3 390 200 ₸ |

Колонка при этом **нигде в расчётах не участвует**: отчёт по кассе
(`routers/reports.build_cash_register_report`) считает Σ сам и уже даёт остатки **по каждой
кассе** (opening / income / expense / closing, JOIN по `t.cash_point_id`); дашборд — тоже Σ.
`balance_after` кассы виден только как столбец «Баланс» в «Регистре денежных средств» (+ в
форме просмотра). `accounts_register.balance_after` (долг по л/с) — корректен, **не трогаем**.

Важная деталь схемы: в `cash_register` **нет** `cash_point_id` (кэшпоинт доступен через
`transactions.cash_point_id`, `transaction_id` — NOT NULL). Сейчас в БД один кэшпоинт «Касса»,
банковских операций нет.

## Решение

**Шаг 1 (сейчас).** `cash_register.balance_after` = **нарастающий остаток денег в кассе после
операции**: Σ(income − expense) по всем строкам в порядке `(operation_date, id)`.
- Инвариант: у последней строки `balance_after == Σ(income − expense)` по всей таблице;
  у каждой строки — Σ по всем строкам до неё включительно.
- Без изменения схемы: при одном кэшпоинте «итог по кассе» = «итог по кэшпоинту».

**Шаг 2 (вместе с 2.15, когда появятся разные кассы/счета).** Добавить
`cash_register.cash_point_id` (миграция + бэкфилл из `transactions`, заполнение в
`insert_cash_register_entry`) и перейти на итог **по кэшпоинту** (`PARTITION BY cash_point_id`) —
раздельные остатки нал/безнал, фильтр/группировка регистра по кассе.

## Изменения в коде (шаг 1)

1. **`backend/models.py`**
   - новая `recalculate_cash_register_balance(executor)` — SQL без фильтра/партиции + guard
     `AND ar.balance_after IS DISTINCT FROM ordered.running` (пишутся только изменившиеся
     строки — важно для повторных пересчётов и массовых операций):
     ```sql
     WITH ordered AS (
         SELECT id, SUM(income - expense) OVER (ORDER BY operation_date ASC, id ASC) AS running
         FROM cash_register
     )
     UPDATE cash_register ar SET balance_after = ordered.running
     FROM ordered
     WHERE ar.id = ordered.id AND ar.balance_after IS DISTINCT FROM ordered.running
     ```
   - `recalculate_cash_balance(executor, account_id=None)` — тонкая обёртка над новой
     (сигнатуру сохраняем: её зовут миграции; `account_id` игнорируется, пересчитывается весь
     регистр — результат идемпотентен);
   - `recalculate_register_balance`/`_RECALC_TABLES` — оставить только для `accounts_register`
     (убрать `cash_register` из набора, чтобы никто случайно не пересчитал кассу «по счёту»);
   - обновить docstring «КОНВЕНЦИЯ ЗНАКОВ» и `CashRegister`.
2. **ORM-события** `transaction_after_insert/update/delete` → `recalculate_cash_register_balance(connection)`.
3. **Индекс**: Alembic-миграция — добавить `(operation_date, id)` для глобального окна
   (существующий `idx_cash_register_account_date (account_id, operation_date, id)` остаётся для
   взаиморасчётов/фильтров).
4. **`backend/field_config.py`**: `cash_register.balance_after` → подпись **«Остаток по кассе»**.
5. **`frontend/src/config/columns.ts`**: колонка `balance_after` → **«Остаток по кассе»**.
6. **Бэкфилл**: новый `backend/migrations/recalc_cash_register_unified.py` (dry-run/`--apply`):
   «до» (последняя строка, Σ по таблице, сколько строк отличается) → `--apply` (штатной функцией)
   → контроль «последняя == Σ». Старый `recalc_cash_register_balance.py` (пересчёт NULL-группы)
   пометить устаревшим в реестре `migrations/README.md`.

## Риски

- **Производительность.** Пересчёт всей кассы на каждую операцию. Сейчас 2 130 строк —
  миллисекунды; guard `IS DISTINCT FROM` пишет только изменившийся хвост. Импортные скрипты
  (`reimport/*`, `migrate_synthetic/*`) пишут в `cash_register` напрямую SQL/Core, поэтому
  ORM-события не срабатывают — квадратичности нет. При росте объёма: ограничить пересчёт
  суффиксом от изменённой позиции либо отключать события на время массового ввода.
- **Смена смысла колонки** — визуальная (это и цель). Отчёты/дашборд/`check_sum` на неё не
  опираются (проверено).
- **`accounts_register` не затрагивается** — там «сальдо по л/с» правильно by design.
