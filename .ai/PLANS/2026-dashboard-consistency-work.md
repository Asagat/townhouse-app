## 3. Открытая разработка (на следующий тред). Читать ДО начала.

### 3.1 Проблема (сформулирована владельцем)
- **Январь‑2022, «Фонд развития»:** в месячном документе начисления по кв были разными (только у 13 л/с по 6 000 —
  «парковка/освещение», а у кв 4,5,10,17 нет). Требуются «персональные начисления» (таких документов не видно).
- **Гипотеза владельца:** если начисление **не по всем л/с** → это фактически **персональное/особое** начисление.
  Иначе при пересоздании месячного документа по регулярным тарифам оно будет «раскидано» некорректно на всех.
- **Ключевой факт из кода:** дата открытия счёта при начислении НЕ учитывается
  (`calculate_accruals_preview`: все активные л/с × все услуги; фильтр только «нет тарифа/нулевой расход»).
  Значит у системы нет механизма отличать «новосёл без начисления» от «перс./особого сбора на часть л/с».

### 3.2 Принятое решение (владелец, __не реализовано__)
- **Направление 2:** учитывать **дату открытия л/с в самом расчёте начислений**.
- **Определение «open_date» (выбрано B):** дата первого **регулярного месячного** начисления
  (`accrual_documents.doc_kind='monthly'`) л/с = момент «ввода/заселения». НЕ «Входящий остаток» (2017‑10),
  т.к. входящие остатки есть у всех и не отражают заселение. (Октябрь‑2017 в данных — только входящий остаток,
  регулярное начинается с 2017‑11.)

### 3.3 План (Направление 2) — по шагам, каждый отдельно валидируется
1. **Миграция** `accounts.opened_at DATE` (Alembic `0020_account_opened_at`), бэкафилл = `MIN(accrual_date`
   по monthly-документам) для активных; показать таблицу «open по л/с». (Примечание: по текущим данным у всех
   почти first monthly=2017‑11; реальное различие открытий проявится для добавленных в будущем л/с.)
2. **Алгоритм:** в `calculate_accruals_preview` / `build_accrual_register_items` (и эндпоинте `generate`) учитывать:
   счёт попадает в месячный документ только если `opened_at <= последний день месяца`. Тесты превью.
3. **Классификация:** после правки алгоритма прогнать аудит — в месячном документе услуги должны покрывать всех
   «уже открытых» л/с; что остаётся не-по-всем или индивидуальным по суммам → вынести в «перс.» (перс-документы).
   Типичные кандидаты: 2022‑01 Фонд (13×6000), добавки по одной кв внутри месячных (кв12 32 000 в 2020‑02,
   кв5 14 000 в 2024‑10 и т.п.), редкие разовые сборы.
4. **Перепроводка регистров** + `check_register_integrity` + контрольные суммы.
5. **Тесты/документация:** pytest; журнал PROJECT_STRUCTURE; заметка ROADMAP.

### 3.4 Пограничный/объёмный вопрос (для владельца)
- Как трактовать историю с «не по всем» в первые месяцы, где у л/с начислений не было вовсе до его появления?
  Если открывать по monthly и применять фильтр **к будущей генерации** — историю не трогаем дальше.
  Если требуется «воспроизводимость» прошлых периодов — объём большой (почти все месяцы 2017‑со старта 16/17).
  Рекомендация: новую логику применять к созданию/пересозданию месячных **вперёд**, историю лишь переклассифицировать
  (без пересчёта дат), т.е. месячный документ = «всем открытым», особое = «перс», новосёл до open — без естественного начисления.
